# API usage and access policy

The runtime specification is served at `/openapi.json`; `/docs` renders Scalar. [client.ts](client.ts) contains generated TypeScript **types**, not an HTTP client implementation. Regenerate with `bun run generate:client`. The specification includes canonical endpoints, legacy aliases and both administrative prefixes.

## Account and session flow

Signup defaults closed. Administrators can create ordinary accounts through `/admin/accounts` or `/api/v1/admin/accounts`, or explicitly enable `open`/`invite` signup. Public registration rejects `roles` and other unknown security fields. Invitation signup uses `X-Signup-Token`. IRC REGISTER obeys signup policy and has no invitation-token mechanism; invite-only provisioning is available through REST/admin.

For initial setup, configure `ADMIN_USERS` and a random `ADMIN_TOKEN`, then provision one reserved name using `POST /api/v1/auth/register` with `X-Bootstrap-Token`. Bootstrap is consumed persistently after administrator provisioning. The bootstrap secret is never accepted as a client/admin bearer token.

```sh
curl -sS "$FLARC_URL/api/v1/auth/login" \
  -H 'Content-Type: application/json' \
  --data '{"username":"Alice","password":"your-account-password"}'
# Response: { ok, account, token, expiresAt }
curl -sS "$FLARC_URL/api/v1/profiles/Alice" \
  -H "Authorization: Bearer $FLARC_SESSION_TOKEN"
```

`token` is a random API credential, expires after 24 hours, and is stored only as a SHA-256 hash server-side. Each account has at most 20 active API sessions. `expiresAt` is Unix milliseconds. Logout (`POST /api/v1/auth/logout`) revokes that token. Password changes, disabling and deletion revoke account sessions. Basic auth, `X-User`, `soju-username`, IRC connection IDs and static administrator tokens do not authenticate an API request. Bearer login is the default. Browser clients can opt into the Secure, HttpOnly, SameSite=Strict `__Host-flarc_session` cookie with `X-FlaRC-Session: cookie` and an allowed exact Origin. That response returns a session-bound `csrfToken` instead of the bearer token. Cookie mutations require the allowed Origin and `X-CSRF-Token`; bearer clients retain their existing behavior.

List or revoke your own devices through `GET /api/v1/auth/sessions` and `DELETE /api/v1/auth/sessions/{id}`. `POST /api/v1/auth/credentials` creates a revocable integration credential with a label, expiry and explicit operation/resource scopes. Effective authority is the intersection of those scopes and current account/resource permissions; a credential cannot delegate broader access. IRC integration clients use `PASS token:<credential>`. There is no automatic refresh-token flow; obtain a new login or scoped credential through the authenticated flow.

IRC uses the same account identity through SASL PLAIN/SCRAM-SHA-256 or `PASS account:password`. NICK/USER alone cannot enter the default network. Registered nickname ownership is enforced after login as well as on initial connection. Service names and aliases cannot be taken by human or ordinary bot sessions. EXTERNAL is unavailable without a certificate authentication implementation. Passwords need the configured minimum length (12 by default). `VERIFY` rejects unsupported verification codes; no email verification or forgot-password flow exists.

## Resource permissions

- Channel names in paths must be URL encoded, for example `%23general`. Authenticated users may read public channel history. Channels with `s`, `p`, `i` or `k` require active/persistent membership or an explicit founder grant; bans deny ordinary reads. A member can read retained history predating their join. A former member loses restricted reads, unless a separate founder grant remains. Administrators have channel administration access.
- Sending via REST requires authenticated channel membership and respects channel moderation. NUL bytes are rejected. The server derives sender identity and role tags; deprecated `senderNick` input is ignored. `Idempotency-Key` prevents duplicate committed messages for the same account/channel/key. Reusing a key with changed content is rejected. Do not infer guaranteed live delivery from a successful commit.
- Edits require the actual author. Channel redaction permits the author or a channel moderator. Redaction scrubs original/edit variants, multiline payloads and search entries. Ordinary authors cannot edit somebody else's message, including by forging an edit tag.
- `GET /api/v1/dms/{target}/messages` uses account names, not transient nicknames. Only actual account participants may read a pair. Administrators get no DM override. Disabled/deleted peers do not remove a surviving participant’s history. Deleted usernames remain reserved, and retained history stays tied to the deleted account ID. Historical nickname-keyed rows are quarantined pending evidence of ownership. Direct conversations also expose stable-ID list/create/detail, send/history/message lookup, edit/redact, read-marker, unread and attachment routes under `/api/v1/conversations`. The `/api/conversations` aliases share those participant checks. Send/edit/redact/read requests use `clientOperationId`; edits and redactions require `expectedRevision`. Group DMs remain unsupported.
- Profiles are readable by authenticated users; writes, read markers, subscriptions and notification preferences are self-only. Public profile changes and IRC METADATA share persisted revisions and authorized event delivery. Supply `expectedRevision` to reject stale updates and use `null` to clear supported fields. Explicit `private:` metadata is owner-only through `/api/v1/metadata/{target}` and never enters public metadata synchronization. Channel role mutations require founder/admin authority. Webhook management requires channel management permissions. Hook execution uses its separate channel-scoped token; `/webhooks/{id}/{token}` also validates the ID.
- Both `/admin/*` and `/api/v1/admin/*` require current network-administrator authority and configured resource/credential scope. Targeted session revocation, account/hostmask bans and optional audit inspection use both prefixes. `AUDIT_LOG_ENABLED` defaults to `false`.
- Ordinary channel operations use their actual channel permissions: `POST /api/v1/channels` creates the founder, membership and initial settings together (secret by default; an existing name returns 409). Channel routes provide join, leave, invitations and revocation, members, inherited roles and bulk redaction. They enforce the same keys, invitations, bans and role hierarchy as IRC. A channel privilege applies only in that channel.
- Authorized channel retirement/re-registration uses a new immutable generation. Old memberships, invitations, permissions, events and media scope cannot transfer to the new resource. Retirement waits for invalidation before name reuse; retained archive data stays separate. User channel deletion takes `purge`, while the administrative delete contract uses `purgeMessages`; consult the operation schema.

History expires after 90 days. Read queries deny expired records even before asynchronous cleanup runs. HTTP history limits cap at 100; IRC history caps at 500. Profile/account enumeration among logged-in users is intentional; restricted-channel discovery is filtered.

## Browser events

Call `POST /api/v1/auth/events-ticket` using the bearer token. Open `/api/v1/events?ticket=...` within 30 seconds; the ticket is single-use and inherits its parent session's lifetime/revocation. Non-browser clients may use an Authorization header on the handshake. Reusable session tokens in query strings do not authenticate. Same-origin sockets are accepted; additional exact origins require `ALLOWED_ORIGINS`.

Channel, conversation and profile events use stable event IDs. Fetch `/api/v1/events/bootstrap`, follow its opaque account-bound `nextPageToken` until `channelsComplete`, then subscribe/replay from its original recovery cursor. Bootstrap includes permitted channel state/history/read markers and conversations. It deliberately preserves overlap between snapshot and replay; clients deduplicate by `eventId`. The snapshot is not globally atomic across Durable Objects. Expired recovery/page cursors return 410 with a resync requirement; obtain a fresh bootstrap. Access is checked against the original audience and current credentials, membership, resource generation and message visibility. A foreign cursor is not an access grant.

The WebSocket accepts typed `subscribe`, `replay`, `bootstrap` and supported `mutate` commands; REST bootstrap/replay and `/api/events` aliases use the same policies. IRC retains PRIVMSG/CHATHISTORY/MARKREAD and exposes structured `CONVERSATION` operations for direct-conversation and recovery parity. Channel read markers still use IRC MARKREAD; direct-conversation markers also have REST and event commands.

Negotiate `flarc.events.v2` for sustained event streams. After reading a `reader.challenge`, send `{"type":"reader.ack","token":"<challenge token>"}` exactly once on that connection. Tokens are unpredictable and connection-specific; acknowledgments confer no mutation or subscription permission. Version 1 emits `resync.required` and closes when acknowledgment becomes necessary. See [the event transport contract](../security/event-stream-topology.md) for bounds and control frames.

At most five event connections per account and 2,000 per network are admitted centrally across server-selected event shards. `EVENT_SHARD_COUNT` defaults to four and is bounded to 1–16. Public transport uses an accepted Worker WebSocket pair to complete native closure while edge Durable Objects retain authorization and hibernating state; the live Worker pair has a deployment cost/lifetime tradeoff. This is not full IRC sharding. Journal count/retention are bounded by `EVENT_JOURNAL_MAX_EVENTS` and `EVENT_JOURNAL_RETENTION_MS`; it is not an unlimited delivery archive.

## Media, previews and notifications

Uploads accept raw bytes (`X-Filename`) or multipart `file`/`media`. `FILEHOST_MAX_UPLOAD_BYTES` sets the per-file byte limit and defaults to 10 MiB; invalid, zero, negative or unsafe values fall back to that default. Multipart requests may use up to 64 KiB beyond the file limit for framing and fields, and the separate account quota remains 100 MiB. Files default to uploader-private. `?channel=%23general` requires channel membership; `?dm=Bob` creates a two-account scope. Channel scopes include an immutable resource generation to prevent attachment inheritance when names are reused. Downloads require Authorization at `/media/{id}` and recheck that scope; ordinary public HTML image tags cannot attach this header, so browser clients need an authenticated fetch/blob URL. Private R2 objects must not be exposed through a public bucket/custom domain. `GET /api/v1/media` lists the authenticated private or explicitly authorized channel/DM scope; `?pending=1` lists only that account’s pending upload reservations. `DELETE /api/v1/media/{id}` is uploader-only. Unowned legacy uploads are unavailable.

Active file formats download as attachments with a sandbox CSP, no-sniff and no-store headers. MIME labels do not establish trusted content; no antivirus, transcoding or automatic attachment-retention workflow exists.

Attachment authorization policy (selected for review): channel uploads require current authenticated membership. Ordinary members can upload in an unmoderated channel; `+m` requires voice/operator status or an assigned custom `attach_files` permission in that channel. This additive permission grants no text sending, role management or ownership, and does not bypass bans, quiet/mute restrictions or read-only metadata; existing voice/operator exemptions for quiet/mute and operator exemptions for read-only remain. Read access is checked separately, so losing upload authority alone does not revoke downloads. SQLite uploads check channel authority before the AccountsDO quota/data transaction; R2 uploads check it at reservation and again after object write, rolling back a rejected pending upload. ChannelDO checks and AccountsDO commits are separate operations: revocation after the last successful channel check can race the commit, so atomic cross-object revocation is not guaranteed.

Outbound previews, hooks and push use the purpose-specific exact HTTPS host grants in `allowlist.yaml`; shipped defaults include common preview hosts and known push providers. Operators can mount the file with `ALLOWLIST_FILE`, use inline `ALLOWLIST_YAML` in Workers, or configure the explicit host-list bindings. Invalid explicit policy fails closed. The local/container adapter rejects private or mixed DNS answers, pins the public destination and refuses redirects; deployed provider egress behavior still requires separate verification. Hook execution is limited to 60 requests/10 seconds per hook.

WebPush stores private HTTPS subscriptions (20/account) and encrypts/signs delivery with configured VAPID credentials. Delivery rechecks current account credentials, recipient access, subscription existence and notification preferences before each attempt. Channel defaults are mentions-only; all/nothing and temporary mute settings apply. Unsubscribing removes queued deliveries so identical endpoint re-registration cannot revive them. Provider 404/410 removes only the affected subscription; transient failures have at most eight attempts with persisted backoff. A request already sent to a provider cannot be recalled. R2 upload cancellation/expiry uses persisted reconciliation; see [deployment policy](../../deploy/README.md).

## Responses and limits

Missing/expired session: 401; authenticated but unauthorized: 403 (some private media is deliberately 404). Invalid inputs/domain mutations commonly return 400; oversized bodies return 413; account/API throttles return 429. Errors follow Nitro/H3 envelopes; see OpenAPI for endpoint-specific responses. Protected HTTP responses use `Cache-Control: private, no-store`.

JSON request bodies cap at 64 KiB, ordinary API requests at 300/minute/account, authentication at 50 requests/10 seconds/IP plus durable credential/signup budgets. WebSocket frames cap at 64 KiB, with IRC command and registration limits. These limits are local engineering controls, not a substitute for deployment/load verification. See [verified tests and remaining limits](../security/security-test-results.md).

IRC rate policy (selected for review): the existing per-socket 150-command/10-second window charges JOIN and PART once per requested nonempty comma-separated target, including repeated or invalid targets; empty entries add no cost. The first target retains the ordinary command charge, and the complete additional cost is checked before dispatch, so an over-budget fanout closes the offending socket without partially applying that command. Single-target commands and malformed-input accounting retain their existing cost; `JOIN 0` remains a one-command leave-all control, and disconnect cleanup still removes memberships. This does not establish account-wide, concurrent-device, reconnect or global creation/retention budgets, nor persistence of the in-memory limiter across runtime recreation.

Online IRC channel renames transfer ACLs, role assignments, message/edit state and scoped media, reject existing destinations, and cap snapshots at 5,000 rows/table and 4 MiB. Partial post-commit failures can require operator reconciliation of the persisted rename journal; there is no automatic distributed transaction/recovery guarantee.

Secure IRC delivery rechecks current credentials and channel authorization per output batch. Pending IRC application queues remain bounded at 4,096 frames/8 MiB per socket and 16 MiB across the coordinator. A separate reader window charges encoded output before native send and limits unacknowledged delivery to 256 KiB, 1,024 frames and 30 seconds. IRC acknowledges unpredictable standard PING/PONG boundaries; event v2 uses its challenge/ACK contract. Oversized or excessive event input is rejected at the public relay before forwarding. These are application bounds with local native-reader tests; they are not universal provider, proxy or OS memory guarantees.
