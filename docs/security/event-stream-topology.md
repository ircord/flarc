# Event connections and acknowledged readers

The network SessionDO remains the authority for IRC nicknames/connections, immutable direct conversations, messages, and the event journal. Event WebSockets use separate SessionDO SQLite identities named `<network>:events:<index>`. `EVENT_SHARD_COUNT` selects a bounded 1–16 shards (default 4). The central authority consumes the endpoint-bound, one-use ticket before deriving an index from its digest. Bearer-header compatibility uses a server-generated seed. Caller account/shard selectors are rejected. Both `/api/v1/events` and `/api/events` obtain central authenticated admission, then the trusted HTTP adapter upgrades the selected edge and explicitly relays an accepted public WebSocket pair; there is no central SessionDO WebSocket forwarding hop. The public pair reciprocates Close frames on both sides so the native TCP stream ends even when the hibernating workerd socket has already exchanged Close frames without releasing its stream. This adds a live Worker transport pair per connection; the edge remains its only application queue, authorization and reader-credit owner, and the adapter retains no payload log. Before forwarding public input it enforces the same 65536-byte UTF8/binary frame bound and 150 frames per ten seconds as the edge, and stops forwarding both directions after an idempotent close. Each edge consumes an internal one-use admission and persists only its actual namespace identity and admission/transport state; its socket attachment holds an opaque connection lease, protocol version, reader counters and cursor acknowledgment, not a bearer token or session hash. Private history stays central.

Central SQLite leases atomically enforce the existing five event connections per account across all event shards and 2000 event connections per network. A lease lasts 30 seconds and is renewed only after current credential/source authorization. Edges poll bounded durable journal hints on separate alarms; the authority never awaits an edge callback that reenters it. Each poll scans at most 1000 rows and selects at most eight currently authorized events. Delivery checks the event again against the original audience, current account/credential, current channel generation/permissions, current conversation participation and canonical message visibility. Legacy public observation remains transient and currently filtered; it grants no historical replay permission. A failed relay closes the affected connection and leaves the central journal intact. Reconnecting clients use the last account-bound cursor or obtain an explicit resync when retention has expired. Payload handoff is not a distributed atomic authorization transaction; revocation concurrent with the final cross-object handoff has the same explicit last-check boundary as F3.

Delivery and cursor advancement are separate: central pending cursors advance only when the edge reports its completed delivery boundary. A wake, interrupted relay or retry can overlap previously delivered IDs; clients deduplicate by `eventId`. Client acknowledgments prove an output boundary, not a domain mutation, and do not invoke subscriptions or message/role writes. Mutation retries still use the domain's durable client-operation identity. The bootstrap cursor-before-registration/snapshot barrier and overlap deduplication contract remains unchanged; there is no global atomic snapshot across Accounts, Channel and Session objects.

For sustained event streaming, clients negotiate the WebSocket subprotocol `flarc.events.v2`. The server sends `{"type":"hello","protocol":2,"ack":{"type":"reader.ack","maxBytes":262144,"maxFrames":1024,"maxAgeMs":30000}}`. A `{"type":"reader.challenge","token":"<32 lowercase hex characters>"}` follows the payload boundary it acknowledges. After reading that boundary, the client sends exactly `{"type":"reader.ack","token":"<same token>"}`. Tokens are unpredictable, connection-specific and one-use. Guessed, foreign, replayed or expired proofs close the connection with 1008. Version 1 connections retain bounded compatibility: at the first required acknowledgment the server emits `resync.required` with `READER_ACK_REQUIRED` and protocol 2, then closes; version 1 is not an unlimited bypass.

IRC uses ordinary `PING :flarc-reader:<token>` and exact `PONG :flarc-reader:<token>` on the same ordered transport. Other ordinary PONGs keep their existing behavior and give no reader credit. Binary IRC challenges retain the binary subprotocol. All output is charged before native send: maximum 256 KiB and 1024 encoded WebSocket frames outstanding, including challenge framing; a frame must fit that window. Event v2 challenges follow 64 KiB or 32 frames; IRC challenges follow 64 KiB or 512 frames so short numeric replies do not trigger per-registration PING traffic. Both retain the 20-second low-volume trigger. IRC challenges wait for the current command, its authorized output queue and any outgoing BATCH to finish, rather than appearing inside a reply; the absolute 256 KiB/1024-frame/30-second limits still fail closed during a response and are never reset by deferral. A response that cannot fit the hard window is still bounded, rather than borrowing unacknowledged credit. Each challenge has a response deadline of at most ten seconds, with an absolute oldest-debt bound of 30 seconds. Only counters/challenge metadata are serialized across hibernation. These are application output bounds and finite local native-reader observations, not universal bounds on Cloudflare, OS, proxy or client buffers.

Decisions for human review: shard count and polling cost, the 30-second lease/reader deadlines, v1 resync behavior, and the output window. IRC connections remain centralized under their existing 2000-network/pending-IP policy; this change does not introduce an account-specific IRC-device quota. Full IRC sharding, deployment-scale capacity, global account/channel retention or creation policies, and provider/OS memory guarantees are outside this topology.

All Session alarm writers share one coalesced earliest-deadline scheduler. The handler explicitly consumes only its fired/past alarm, retaining concurrently scheduled future deadlines. Reader state is persisted through the final challenge boundary before arming its future timeout; closed windows stop delivery and do not rearm due-now alarms.

REST and event-command channel sends commit their IRC delivery intent in the same SQLite transaction as the message. The channel drains these intents in commit order, checks current generation and message visibility, and retries failed RPC delivery through its alarm. A caller waits through its committed intents on a healthy drain; a delivery failure leaves durable retry work without turning a committed message into a failed write. Central SessionDO keeps one expiring internal delivery-sequence receipt per channel in the operation store, preventing a lost RPC acknowledgement from duplicating the IRC enqueue, including after hibernation. Recipients still pass current membership and credential checks. The receipt records server enqueue, not client receipt; runtime failure between enqueue and network delivery still requires history/replay recovery and does not provide exactly-once network delivery.

The ordered delivery call explicitly disposes its RPC promise in `finally`, including on rejection. Without that cleanup, the injected lost acknowledgement prevented forced hibernation even after the durable write and IRC delivery completed. The regression checks a different reconstructed instance with all three sockets retained, the same SQLite receipt, and a retry without duplicate delivery. This follows the [Workers RPC lifecycle contract](https://developers.cloudflare.com/workers/runtime-apis/rpc/lifecycle/).
