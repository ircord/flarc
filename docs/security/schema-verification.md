# SQLite deployment schema verification

Build the diagnostic with `bun run build:tools`, then run it against a stopped deployment's persistent volume or a consistent SQLite backup:

```sh
node .output/tools/verify-schema.mjs /data/do > schema-report.json
```

The container includes the compiled diagnostic. A directory scan requires recognized Accounts, Channel and Session databases; a single `.sqlite` filename verifies that database alone. Uninitialized or unrelated databases are reported as `NOT APPLICABLE`, never as a successful FlaRC schema. Missing domain databases fail the directory check. Files are opened read-only and inspected inside read transactions. The tool reads schema metadata, not accounts, credentials, messages or other application rows. It does not migrate, repair or initialize storage.

For a read-only mounted volume, stop its application first and copy the complete SQLite directory, including `-wal` and `-shm` siblings, into a private writable temporary directory before inspection. SQLite may need auxiliary lock files even for a read-only connection. Do not discard WAL files or use `immutable=1` to bypass this: either can omit committed state. The release container smoke check follows this stopped-copy procedure and removes its disposable volume afterward.

The JSON report compares exported Drizzle models with actual columns, SQLite types, nullability, defaults, ordered primary keys, unique constraints, named indexes, grouped foreign keys and CHECK expressions. Additional nonunique performance indexes are listed. Missing models, extra columns, unexpected unique constraints and constraint differences fail the check. Expression and partial indexes whose expressions cannot be verified also fail. CHECK comparison is structural, with quoting and whitespace normalization; semantic equivalence of different SQL expressions is not inferred. SQLite-managed implicit indexes and the INTEGER PRIMARY KEY rowid rule are recognized explicitly.

Exit codes are `0` for a matching modeled schema, `1` for differences or incomplete domain coverage, and `2` for invocation/read errors. A passing schema comparison is not a data-integrity check, a migration replay test, or proof of authorization. Trigger behavior, collations outside modeled indexes and provider behavior need their dedicated tests. The domain verifier checks the exact FTS declaration and generated shadow-table layouts separately, lists reserved provider tables without reading them, and rejects other unmodeled application tables.

The inherited schema contains TEXT PRIMARY KEY columns without explicit NOT NULL constraints. SQLite permits nulls there while Drizzle's column-level `primaryKey()` declares non-null. The diagnostic deliberately reports these differences. Earlier test allowances do not turn them into schema equivalence. The diagnostic never rebuilds tables.

`server/storage/migrations/primary-nullability.ts` implements a separate transactional repair, invoked once at schema version 1000 by all three production Durable Object constructors after schema initialization. It stages approved tables and their complete foreign-key dependents within SQLite, drops children before parents, and restores original row identities, values, indexes, triggers and AUTOINCREMENT high-water marks. Foreign-key enforcement stays enabled. NULL legacy identities, unapproved dependents, cycles and unsupported layouts fail before destructive work; failures during staging, dropping or restoration roll back the transaction. Four real workerd/SQLite helper tests verify Accounts, Channel and Session rollback and preservation, using independently registered accounts, actual scoped credentials, independent reads and runtime recreation. Two additional integrated startup tests verify strict schema parity, real IRC hibernation and automatic upgrade from restored legacy nullable keys.

The automatic repair is bounded to databases of 32 MiB and 100,000 affected rows. Larger databases need an explicit maintenance migration; these limits do not change message retention or delete data. Size comes from the documented [SqlStorage.databaseSize property](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#databasesize), since workerd rejects `PRAGMA page_size`. The bounds can be raised explicitly with SQLITE_MIGRATION_MAX_BYTES and SQLITE_MIGRATION_MAX_ROWS during a planned maintenance window; the operation can still roll back if runtime limits are reached. These local tests do not establish equivalence for an existing remote deployment.

For Cloudflare, this diagnostic requires a supported consistent SQLite export or a separate metadata verification path; a local Miniflare/container result is not evidence of the deployed Cloudflare schema. No remote deployment has been inspected or modified by this work.
